# issue-planner（コマンド）

ユーザーの雑な指示を GitHub Issue 化する入口。**このコマンドはユーザーと直接会話しているセッション（オーケストレータ）で実行されるため、`grillme` スキルや `AskUserQuestion` でユーザーに直接質問できる**。

`.claude/agents/issue-planner.md`（サブエージェント）は対話ツールが渡らずユーザーに質問できない。そのため「ヒアリング → エージェント起動 → 残論点の再質問」の順序をこのコマンドで固定し、ヒアリングの抜け漏れを防ぐ。

## 引数

`$ARGUMENTS` = ユーザーの雑な指示（空の場合は直前の会話からIssue化したい内容を拾う。それも無ければ「何をIssue化しますか？」と聞く）

## 手順

### Step 1. 事前コード調査（軽く）

質問の質を上げるため、指示に関係しそうな箇所を `Grep`/`Glob`/`Read` で軽く確認する。`docs/decisions.md` の関連エントリも確認する。
- 目的は「コードを読めば分かることをユーザーに聞かない」こと。深い影響範囲調査は Step 3 のエージェントに任せる

### Step 2. grillme でヒアリング（必須・省略しない）

`Skill` ツールで `grillme:grillme` を起動し、ユーザーにクエスチョン形式で深掘りインタビューする。**やり取りは日本語で行う**。

最低限、以下が埋まるまで質問を続ける（Step 1 で判明済みの項目は聞かない）:
- **目的**: 何を達成したいか / 誰（親・子）のどの画面・機能か
- **背景**: なぜ今必要か、現状の何が困っているか
- **期待する挙動**: 完成形の具体例（文言・表示・数値など）
- **スコープ**: 含めるもの / 含めないもの
- **仕様の分岐点**: 実装方針が複数考えられる箇所はどちらを採るか（選択肢を示して聞く）
- **エッジケース**: 境界値・例外時の扱いで判断が必要なもの

質問は `AskUserQuestion`（選択肢付き・推奨案を先頭）を優先し、自由記述が必要なものだけテキストで聞く。ユーザーが「おまかせ」「そこは任せる」と答えた項目は、推奨案を採用した旨を記録して次へ進む。

ヒアリングの最後に、まとめ（目的・背景・期待挙動・スコープ・決定事項・おまかせ項目）を提示し、ユーザーの了承を得る。

### Step 3. issue-planner エージェントを起動

`Agent` ツールで `subagent_type: issue-planner` を起動する。プロンプトには以下をすべて含める（エージェントは会話履歴を見られない）:
- ユーザーの元の指示（原文）
- Step 2 のヒアリング結果まとめ（決定事項・おまかせ項目を区別して）
- Step 1 の事前調査結果（関連ファイル・関連する decisions エントリ）

### Step 4. 残った要確認事項をユーザーに質問

エージェントの報告に「要確認事項」がある場合:
1. `AskUserQuestion` でユーザーに質問する（エージェントが示した選択肢を使う）
2. 回答を Issue にコメント追記する（`"C:\Program Files\GitHub CLI\gh.exe" issue comment <N> --body-file <tmp>`）。本文の「要確認事項」への回答であることが分かる形で書く
3. 回答で要確認事項がすべて解消した場合は、Issue 本文の「自動着手について」の評価を見直す必要があるか判断し、必要なら `gh issue edit <N> --body-file <tmp>` で本文を更新する（**`auto-pickup` ラベルは付けない**）

### Step 5. 報告

以下をユーザーに報告する:
- Issue URL・タイトル
- スコープ評価（自動着手向き / 非推奨）と理由
- 要確認事項の解消状況
- 「自動着手させる場合は `auto-pickup` ラベルを付与してください」という案内

## やってはいけないこと

- **Step 2 のヒアリングを飛ばして Step 3 に進まない**（指示が具体的に見えても、最低限の確認はする。エージェント内では質問できないため、ここで聞かなかった論点は憶測で埋まるか「要確認事項」に残るだけになる）
- `auto-pickup` ラベルを付与しない（`docs/未実装仕様書/issue-auto-pipeline.md` 2章の安全原則。付与は常に人間）
- Issue 化のついでにコードを変更しない
