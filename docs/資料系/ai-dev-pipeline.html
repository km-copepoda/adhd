登場人物

あなた（人間）

やりたいことを投げる。Issue の中身を見て着手を許可する。最後にマージする。判断だけを担当し、実装作業はしない。

Claude Code

役割ごとのサブエージェント群（issue-planner / policy-checker / test-writer / implementer / code-reviewer / pr-submitter）が Issue 化と TDD 実装を担う。

Codex

GitHub App（chatgpt-codex-connector）。起票直後の Issue ドラフトのレビュー相手であり、PR に対しては致命的バグ・脆弱性に絞ったレビューを返す。

サブエージェントと担当モデル

Issue 化の issue-planner だけ Opus ── 設計判断の質がそのまま成果物の質になるため。実装〜レビューの実務は Sonnet で回す。 /issue-picker と /codex-followup はサブエージェントではなくスラッシュコマンドで、Claude Code のメインセッション上で動き、必要に応じて下のエージェントを呼び出す。

エージェントモデルツール役割
issue-planner Opus Read / Grep / Glob / Bash 雑な指示を深掘りして Issue 起票（gh issue create）
policy-checker Sonnet Read / Grep / Glob 規約・方針との衝突、非標準アプローチの検出
test-writer Sonnet Read / Grep / Glob / Write / Edit / Bash Red: src/__tests__/ に失敗テストを書く（境界値含む）
implementer Sonnet Read / Grep / Glob / Write / Edit / Bash Green + Refactor: テストを通す最小実装 → 規約準拠に整理
code-reviewer Sonnet Read / Grep / Glob / Bash XP・進化・ステータス遷移・日付・集約ロジックの規約準拠を最終チェック
pr-submitter Sonnet Read / Grep / Glob / Bash ブランチ作成・コミット・push・PR 作成・@codex review 投稿
/issue-picker コマンド メインセッション auto-pickup Issue を 1 件拾い、上記フローに乗せる
/codex-followup コマンド メインセッション Codex レビューの取得・対応・再依頼を 1 反復。/loop で反復実行

6 つのフェーズ

01You

やりたいことを投げる

整形されたチケットは不要。一文の要望や不具合報告をそのまま渡す。

入力例
「クエスト一覧の表示が遅いから直して」「宝箱にレアリティ表示を足したい」
やること
思いついたことを言葉にするだけ。背景の整理や影響範囲の調査は次のフェーズに任せる。
02Claude

Claude が Issue を起票する

issue-planner エージェントが、雑な指示を「考え抜かれた Issue」に変換する。指示をそのまま貼り付けることはしない。

使うもの
issue-planner（深掘り担当）→ gh issue create
掘り下げる項目
  • 目的 / 背景（元の指示も引用）
  • 実装方針（複数案あれば比較して推奨を 1 つ）
  • 影響範囲（波及するファイル・API・DB・集約ロジック）
  • テスト要件と境界値・エッジケース
  • スコープ評価（自動着手向き / 非推奨）を本文に推奨として記載
出力
ラベルなしの Issue ドラフト（+ URL 通知）
まだ着手許可は出ていない ── この時点では Issue はドラフト段階。次のフェーズで Codex レビューを挟み、問題がなければ人間に差し戻される。
03Codex × Claude

Codex と Issue をレビューする

起票した Issue ドラフトを Claude が Codex に渡してレビューしてもらう。目的・実装方針・影響範囲・テスト観点に穴がないかを往復で詰め、問題がなければ人間に差し戻す。

レビュー
Claude が Issue 内容を Codex に共有し、方針の穴・考慮漏れ・過剰スコープなどの指摘を受ける。
反映
指摘があれば Claude が Issue 本文を修正して再レビュー。
完了
Codex が「問題なし」と返したら、レビュー済みの Issue を人間に差し戻す。
人間ゲート 1｜着手許可 ── レビュー済みの Issue を人間が確認し、auto-pickup ラベルを付ける。ここで初めて着手が許可される。ラベル付与は必ず人間の操作で、AI がスコープを自己判定して自分に許可を出す経路は塞いでいる。
補足 ── 現状この Codex レビューは会話ベースで手動。プロジェクト規約との機械的な衝突チェック（policy-checker）は次フェーズの issue-picker 内で自動実行される。
04Claude

テストファーストで実装する

issue-picker が auto-pickup の付いた Issue を 1 件拾い、規約チェック → Red → Green → Refactor を回してから PR を作る。

拾い方
作成日が最も古い 1 件のみ（同時進行はしない）。専用 worktree + ブランチ issue-<N>-<slug>、base は develop。
規約チェック
policy-checker が docs/decisions.md と CLAUDE.md を読み、方針と逆行しないか確認。衝突すれば実装せず auto:blocked にして人間へ差し戻す。
TDD ループ
  • test-writer — src/__tests__/ に失敗テストを書き npm test で赤を確認（境界値含む）
  • implementer — テストを通す最小実装 → 規約準拠にリファクタ
  • code-reviewer — XP タイミング・進化ロジック・ステータス遷移・集約ロジック・日付処理を照合
  • APPROVED が出るまで implementer ⇄ code-reviewer を最大 3 反復
PR 作成
pr-submitter がコミット・push・PR 作成し、@codex review を投稿。Issue は auto:pr-open へ。
05Codex

Codex がレビューし、Claude が反復対応する

/loop /codex-followup が「レビュー取得 → 対応 → 再依頼」を自動で回す。最大 20 反復。

レビュー方針
Codex には「動作不能バグ（Fatal Bug）と明確なセキュリティ脆弱性のみ、重要度順に最大 3 件」を依頼。些細な指摘は出させない。
指摘の処理
  • UI / ロジック・パフォーマンス / QA の 3 カテゴリに判定し、implementer に重点確認事項を注入
  • コード修正を伴う指摘は必ず先に失敗テストを追加（回帰テスト必須）
  • 規約と衝突する指摘は直さず日本語で理由を返信
  • 1 反復 = 1 コミット以下、処理済みは 👀 リアクションで管理
完了条件
CI green ＋ Codex 承認 ＋ マージ可能（mergeStateStatus == CLEAN）。ここで 「MERGE READY」を通知して停止する。
06You

問題なければマージする

MERGE READY 通知を受けた人間が最終確認してマージする。マージだけは意図的に自動化しない。

人間の作業
差分と Codex のやり取りを確認し、develop へマージ。
後処理
develop ベースでは Closes #N が効かないため、マージ検知後に gh issue close ＋ auto:done へ遷移させる。
人間ゲート 2｜マージ判断 ── /codex-followup は「通知して止まる」設計。実際にマージするのは常に人間。

Issue ラベルで状態を管理する

DB や外部ストアを持たず、GitHub Issue 自体を状態機械にする。auto:* 系は自動化プロセスだけが付け外しし、人間は触らない。

auto-pickup

このIssueは自動着手してよい、という人間の明示的な許可。これが無ければ絶対に着手しない。

人間が付与
auto:in-progress

issue-picker が着手。worktree で実装中。

issue-picker
auto:pr-open

PR 作成済み。/codex-followup がレビュー反復を回している。

issue-picker
auto:merge-ready

CI green・Codex 承認・マージ可能。人間の操作待ち。

codex-followup
auto:blocked

方針衝突、またはレビュー反復上限で自動化を断念。人間の判断が必要。

picker / followup
auto:done

PR マージ済み、対応完了（終端）。

マージ後処理

人間が必ず介在する 3 点

着手を許可する

Codex レビューを通った Issue を読み、auto-pickup ラベルを付ける。スコープが大きすぎる・曖昧な Issue はここで弾く。

ブロックを解除する

auto:blocked になった Issue は自動リトライしない。人間が対応してラベルを付け直すまで放置される。

マージする

MERGE READY 通知を受けて最終確認し、自分でマージする。パイプラインはここまで来て止まる。

現在の実装状況

要素状態補足
issue-planner エージェント 実装済み 深層思考で Issue 起票。Issue #15 で動作確認済み。
サブエージェント 5 種 実装済み policy-checker / test-writer / implementer / code-reviewer / pr-submitter。既存の対話フローと共通。
issue-picker コマンド 実装済み Step 0〜8 を手動で通し検証済み。
/codex-followup（カテゴリ判定込み） 実装済み 最大 20 反復。指摘のカテゴリ別コンテキスト注入まで記述済み（Codex 実レビューでの検証は未）。
GitHub ラベル 6 種 実装済み auto-pickup ほか作成済み。
Codex との Issue レビュー 手動運用 起票直後の Issue を Codex に見てもらう工程。現状は会話ベースで手動。専用の自動ステップは未整備。
各エージェント / コマンドの起動 手動運用 issue-planner と issue-picker はそれぞれ手動でキックする。
Issue / ラベルを検知する自動トリガー 未配線 RemoteTrigger の webhook（issues.labeled）＋ schedule のクラウドルーティンが未接続。ここが繋がると全自動化。
マージ 自動化しない 設計上の意図。常に人間が実行する。
まとめ ── 中身（エージェント・コマンド・ラベル）は揃っている。残りは「Issue に auto-pickup が付いたのを検知して issue-picker を自動起動する配線」だけ。それまでは各ステップを手動でキックして運用する。

安全装置

  • auto-pickup の無い Issue には絶対に着手しない
  • 着手前に必ず policy-checker を通す
  • 同時に処理する Issue は 1 件まで
  • 反復上限は 2 種（1 指摘あたり 3 回 / PR 全体で 20 回）。到達したら人間にエスカレーション
  • auto-pickup 付与後に Issue 本文が編集されていないか検証（プロンプトインジェクション対策）
  • main への直接コミット・直接 PR は禁止（base は常に develop）
  • npm test が通らないコードは push しない
  • auto:blocked の Issue を自動リトライしない
  • マージは自動化しない
