# ごほうびシステム 設計書



> 作成日: 2026-05-27

> ステータス: 設計中（未実装）



---



## 1. 概要



子供のクエストクリアに対して「現実世界の報酬」を接続する仕組み。

ゲーム内報酬（XP・進化・バッジ）だけでは 2〜3 週間で飽きるリスクがあるため、

親が設定した現実のごほうびをゲーム体験に組み込む。



### 設計方針



- **既存の XP → 進化ループを壊さない**（XP は消費しない。通貨の追加もしない）

- **親の設定負荷を最小にする**（テンプレートで即開始）

- **間欠強化（Variable Ratio Schedule）を活用** — 「もらえるかもしれない」が最も行動を持続させる。ADHD の子は特にこの「かもしれない」への感受性が高い

- **子供の自発的動機を促す仕組み** — 親の代理操作では宝箱は出ない



---



## 2. 宝箱の仕組み



### コンセプト



```

子供がタスクを報告 → 🔒 ロック宝箱をゲット（貯まっていく）

親が承認する    → 🔓 宝箱がアンロックされる

好きなタイミング  → アンロック宝箱を開封！

 → 当たり: ごほうびが入ってる！🎉

 → ハズレ: 「モンスターがよろこんでいる！✨」

```



- **宝箱は必ず出る**: minTasks 達成で1個、全完了でもう1個

- **報告時はロック状態**: 親が承認するとアンロックされる

- **開封は子供が決める**: アンロック宝箱を好きなときに開けられる

- **中身は開封時に抽選**: 当たりならごほうび、ハズレならポジティブ演出

- **天井あり**: 連続ハズレを防止

- **鍵という概念はない**: 宝箱が LOCKED → UNLOCKED → OPENED と遷移するだけ



### なぜこの構造か



| 問題 | 解決 |

|------|------|

| 嘘報告で中身を取れる | ロック状態なので承認されないと開けない |

| 親が承認を放置すると子供が損する | 「宝箱あるから承認して！」と子供がせがむ |

| 確定報酬だと飽きる | 中身がランダムなので間欠強化が効く |

| 宝箱が出ない（ハズレ）とモチベ低下 | 宝箱自体は必ず出る。中身が抽選 |

| 「いつ開けるか」の自由がない | 子供が好きなタイミングで開封 |

| まとめ開けで全ハズレだと大ダメージ | 天井（5連続ハズレで次は確定当たり） |

| 宝箱と鍵の個数がズレて管理が面倒 | 鍵を廃止。宝箱の状態遷移だけで完結 |

## 3. 宝箱の獲得条件



| タイミング | 条件 | 宝箱 |

|-----------|------|------|

| 1個目 | その日の報告完了数 ≥ minTasksForStreak | 通常宝箱 |

| 2個目 | その日の全クエストを報告完了 | ボーナス宝箱（開封時に確率2倍） |

| なし | minTasks 未達 | 出ない |



- **minTasks 未達 → 宝箱なし** — 1個やっただけで宝箱が出て残りをサボる問題を防ぐ

- **親の子画面モード（代理操作）→ 宝箱なし** — 子供の自発的動機を促す仕組みのため、親が代理で報告+承認した場合は宝箱を生成しない



### 自動承認の場合



| 条件 | 宝箱 |

|------|------|

| minTasks 達成 or 全完了 | 1個のみ（通常宝箱）、即 UNLOCKED |

| minTasks 未達 | なし |



- 自動承認は翌日にまとめて処理される

- 2個出ても文脈がわからないため1個に制限

- 承認と同時なので LOCKED を経ずに UNLOCKED で生成

## 4. 宝箱の状態遷移



```

LOCKED（ロック中）

 → 報告時に生成。承認待ち。子供は数を確認できるが開けられない



UNLOCKED（アンロック済み）

 → 親が承認すると遷移。子供が好きなときに開封できる



OPENED（開封済み）

 → 子供が開封。中身の抽選結果が確定

 → 当たり（itemId あり）→ 親の「渡したよ」待ち → fulfilled = true で完了

 → ハズレ（itemId なし）→ ポジティブ演出のみ。完了



CANCELLED（破棄）

 → 親の差し戻しにより minTasks を下回った場合、LOCKED 宝箱を破棄

```



```

報告時 → [LOCKED] → 承認 → [UNLOCKED] → 開封 → [OPENED] → 渡した → fulfilled

         → 差し戻し → [CANCELLED]

自動承認時 → [UNLOCKED]（LOCKED をスキップ）→ 開封 → [OPENED]

```

## 5. レア度と抽選確率



| レア度ラベル | enum | 通常宝箱 | ボーナス宝箱（全完了で獲得、確率2倍） |

|-------------|------|---------|--------------------------------------|

| よく出る | COMMON | 1/7（≈14%） | 2/7（≈29%） |

| ときどき | UNCOMMON | 1/14（≈7%） | 2/14（≈14%） |

| たまに | RARE | 1/28（≈4%） | 2/28（≈7%） |

| ハズレ | — | 上記いずれにも当たらなかった場合 | 同左 |



- 子供は確率を知らない。体感で「全部やったときの宝箱は当たりやすいな」と学習する

## 6. 天井（ピティシステム）



連続ハズレを防止する仕組み。



```

5回連続ハズレ → 次の開封（6回目）は COMMON 以上が確定で当たる

```



- カウンターは子供ごとに管理（User.treasurePityCount）

- 当たりが出たらカウンターリセット

- 天井の存在は子供に明示しない（裏で動く）

- 宝箱プールが空の場合は天井カウンターを進めない



---



## 7. 抽選ロジック



```

drawTreasure(childId, options?): TreasureItem | null



1. 子供の宝箱プールから有効な（isActive = true）アイテムを全取得

2. プールが空なら null（ハズレ演出のみ。天井カウンターは進めない）

3. options.boosted = true なら確率を2倍にする

4. 各レア度ごとに1回独立に抽選（プールに何個アイテムがあっても確率は変わらない）

  - COMMON:  1/7 （boosted: 2/7）

  - UNCOMMON: 1/14 （boosted: 2/14）

  - RARE:   1/28 （boosted: 2/28）

5. 当たりが複数ある場合 → 一番レアなものを優先

6. 当たりレア度のアイテムをプールからランダムに1個選ぶ（同レア度に複数アイテムがあれば均等抽選）

7. 当たりレア度のアイテムがプールに無ければ次に低いレア度の当たりに降格、いずれも無ければハズレ

8. 全ハズレなら天井チェック: pityCount >= 5 でプールから1個強制ピック → カウンターリセット（天井発動）

9. 当たり → カウンターリセット → TreasureItem を返す

10. ハズレ → カウンター +1 → null を返す

```

## 13. 子供ごとの設定



ごほうびは **子供ごとに個別設定** する（家族共通テンプレートは作らない）。



### 理由



- 兄弟で欲しいものが違う（年齢・性別・好み）

- このアプリは既にタスク・締切・ストリーク条件を子供ごとに分けている

- 子供は多くても 2〜3 人。設定が倍でも負担は小さい

- 「共通＋上書き」は親が管理画面で混乱するリスクが高い

## 14. DB スキーマ（案）



```prisma

/// 宝箱プールのごほうびアイテム

model TreasureItem {

 id    String  @id @default(cuid())

 childId  String

 child   User   @relation(fields: [childId], references: [id], onDelete: Cascade)



 title   String      // 「おやつをひとつ選べる」

 rarity  TreasureRarity  // COMMON / UNCOMMON / RARE

 sortOrder Int  @default(0)

 isActive Boolean @default(true)



 logs   TreasureLog[]

 createdAt DateTime @default(now())

 updatedAt DateTime @updatedAt

}



enum TreasureRarity {

 COMMON   // よく出る: 1/7（ボーナス宝箱: 2/7）

 UNCOMMON  // ときどき: 1/14（ボーナス宝箱: 2/14）

 RARE    // たまに:  1/28（ボーナス宝箱: 2/28）

}



/// 宝箱のライフサイクル管理

model TreasureLog {

 id    String  @id @default(cuid())

 childId  String

 child   User   @relation(fields: [childId], references: [id], onDelete: Cascade)

 date   DateTime @db.Date // 獲得日（JST を UTC 0:00 として保存）



 trigger  TreasureTrigger

 boosted  Boolean @default(false) // 全完了ボーナス宝箱（確率2倍）

 status  TreasureStatus @default(LOCKED)



 // 開封結果（開封前は null）

 itemId  String?

 item   TreasureItem? @relation(fields: [itemId], references: [id])

 openedAt DateTime?   // 開封日時



 // 当たりの場合の受け渡し管理

 fulfilled Boolean @default(false) // 親が「渡したよ」を押したか



 createdAt DateTime @default(now())

 updatedAt DateTime @updatedAt

}



enum TreasureTrigger {

 STREAK    // ストリーク達成（minTasks クリア）

 ALL_COMPLETE // 全タスク完了

 AUTO     // 自動承認

}



enum TreasureStatus {

 LOCKED   // 🔒 報告時に生成。承認待ち

 UNLOCKED  // 🔓 承認済み。子供が開封可能

 OPENED   // 📦 開封済み。中身確定

 CANCELLED  // ❌ 差し戻しにより破棄

}



/// User モデルに追加するフィールド

// treasurePityCount Int @default(0) // 天井カウンター（連続ハズレ数）

```



### テーブル設計の意図



- **TreasureItem**: 宝箱プール。`title` + `rarity` のみ

- **TreasureLog**: 宝箱1個 = 1レコード。状態遷移で全ライフサイクルを管理

 - `status` で LOCKED → UNLOCKED → OPENED の遷移を追跡

 - `boosted` フラグで通常 / ボーナス宝箱を区別

 - `itemId` + `openedAt` は開封時にセット

 - 鍵は不要。承認されたら宝箱自体がアンロックされる

- **User.treasurePityCount**: 天井カウンター。ハズレで +1、当たりで 0 リセット

## 16. 処理の組み込み箇所



### 報告時（宝箱生成）



```

src/app/api/quests/[id]/report/route.ts

 → 報告処理の後にその日の報告完了数をカウント

 → minTasks 達成 → TreasureLog 生成（status=LOCKED, trigger=STREAK）

 → 全完了   → TreasureLog 追加生成（status=LOCKED, trigger=ALL_COMPLETE, boosted=true）

 → レスポンスに宝箱獲得情報を含める

```



### 承認時（アンロック）



```

src/lib/approve.ts — approveQuestInstance()

 → 承認後、その子供の同日の LOCKED 宝箱を UNLOCKED に更新

```



### 開封時（抽選実行）



```

src/app/api/treasures/open/route.ts（CHILD 用）

 → UNLOCKED の TreasureLog があるか確認（なければ 400）

 → 最も古い UNLOCKED 宝箱を取得

 → drawTreasure() で中身を抽選（boosted なら確率2倍）

 → itemId + openedAt をセット、status → OPENED

 → 天井カウンター更新

 → 当たりの場合、親に通知

```



### 差し戻し時（宝箱破棄）



```

src/app/api/approve/[id]/route.ts（差し戻し処理）

 → 差し戻しにより minTasks を下回った場合、LOCKED 状態の TreasureLog を CANCELLED に

```



### 自動承認時



```

src/app/api/cron/auto-approve/route.ts

 → 子供ごとにまとめて承認

 → 条件を満たす場合、宝箱を1個だけ生成（trigger=AUTO, status=UNLOCKED）

 → 翌朝アプリ起動時に宝箱ストック増加を通知

```



### 親の子画面モード（代理操作）



```

src/app/parent/child-view/ からの報告+承認

 → 宝箱を生成しない（proxy フラグで制御）

 → XP・進化・ストリーク等の通常処理は行う

 → 子供の自発的行動ではないため宝箱の対象外

```



### 抽選ロジック



```

src/lib/treasure.ts（新規）

 → drawTreasure(childId, options?): TreasureItem | null

 → options.boosted = true で確率2倍

 → 天井チェック込み

 → null = ハズレ（ポジティブ演出のみ）

```

## 19. 決定済み事項



- [x] **⭐通貨・交換ショップは作らない** — 宝箱抽選のみのシンプル構造。通貨管理・インフレ・事前承認の複雑さを排除。

- [x] **ごほうびは子供ごとに個別設定** — 兄弟で欲しいものが違う。家族共通＋上書きは親が混乱する。

- [x] **デイリークエスト方式は採用しない** — タスク構成が家庭ごとに違うため達成不可能な条件が出る。ADHD の子に「自分ではどうしようもない」条件を課すのは逆効果。「いつも通りをやったら、たまにいいことが起きる」構造が正しい。

- [x] **minTasks 未達では宝箱なし** — 1個完了しただけで宝箱が出て残りをサボる問題を防止。

- [x] **全完了時は確率2倍（確定ではない）** — 間欠強化（Variable Ratio Schedule）を活用。「もらえるかもしれない」が最も行動を持続させる。確定報酬にすると間欠強化が崩れる。子供は確率を知らないが体感で「全部やると当たりやすい」と学習する。

- [x] **自動承認でも宝箱は出る（ただし1個・通常確率のみ、即 UNLOCKED）** — 親が非協力的でも子供の努力が無駄にならない。まとめて承認されると2個出ても文脈がわからないため1個に制限。都度承認なら最大2個（親が積極的に承認するインセンティブにもなる）。

- [x] **宝箱は必ず出る。中身が抽選** — 宝箱が出ない（ハズレ）を見せるとモチベ低下。宝箱自体は毎回出して「開ける体験」を提供する。ハズレ時はポジティブ演出（「モンスターがよろこんでいる！」等）で「何も出なかった」感を消す。

- [x] **宝箱は貯められる。開封は子供が好きなタイミングで** — 「いつ開けるか」の自己決定感。まとめ開けのガチャ的ワクワク。

- [x] **天井（ピティ）あり: 5連続ハズレで次は COMMON 以上確定** — まとめ開けで全ハズレの絶望を防止。天井の存在は子供に明示しない。

- [x] **鍵を廃止。宝箱のステータス遷移で管理** — 宝箱と鍵の個数ズレ問題を排除。LOCKED → UNLOCKED → OPENED の遷移だけで完結。

- [x] **嘘報告防止: 報告で宝箱（LOCKED）、承認でアンロック** — 報告しただけでは開けられない。中身の抽選は開封時。

- [x] **親の子画面モード（代理操作）では宝箱を生成しない** — 子供の自発的動機を促す仕組みのため。XP・進化・ストリーク等の通常処理は行うが、宝箱は対象外。
