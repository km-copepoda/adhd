# シングルユーザーToDoアプリ仕様書

作成日: 2026-08-05

## 概要

親子版 QuestBoard の育成エンジン（進化・転生・ストリーク・バッジ・コレクション・テーマセット）をそのまま活用し、**一人で使えるタスク管理 × モンスター育成アプリ** を別アプリとして開発する。

### コンセプト

> **自分のタスクを自分で管理して、モンスターを育てる。**

- ターゲット: ADHD当事者の中高生〜大人、タスク管理が苦手な人全般
- 親承認なし。タスクの完了は自己申告制
- 「モンスターを育てたいから嘘つかない」が動機づけとして機能する

### 親子版との差分サマリ

| 要素 | 親子版 | シングル版 |
|------|--------|-----------|
| アカウント構造 | Family → Parent + Child | 1ユーザー（ロールなし） |
| タスク作成者 | 親が作成 | 自分で作成 |
| 承認フロー | REPORTED → 親が APPROVED/REJECTED | REPORTED → 即 APPROVED（自動） |
| 通知 | 親↔子の双方向 | 自分へのリマインドのみ |
| 進化・転生・図鑑 | 共通 | 共通 |
| ストリーク・バッジ・XP | 共通 | 共通 |
| コレクション・宝箱 | 共通 | 共通 |
| テーマセット（買い切り） | 共通 | 共通 |
| サブスク制限 | 子アカウント数・タスク数 | タスク数のみ（子アカウントの概念なし） |

---

## 1. アカウント構造

### 1.1 ユーザーモデル

親子版の `Family` モデルと `Role` enum を廃止し、単一ユーザーモデルにする。

```
親子版:
  Family ─┬─ User (PARENT)
           └─ User (CHILD) ← モンスター・XP・進化はここに紐づく

シングル版:
  User ← モンスター・XP・進化・タスク、全てここに紐づく
```

### 1.2 DB差分

**削除するもの:**
- `Family` モデル
- `User.familyId`
- `User.role` (Role enum)
- `TaskTemplate.assignedChildId`（タスクは常に自分のもの）

**変更するもの:**
- `QuestInstance.childId` → `QuestInstance.userId`（名前の変更のみ）

**そのまま使うもの:**
- `User` のモンスター関連フィールド（evolutionStage, evolutionPath, studyPt, etc.）
- `TaskTemplate`（assignedChildId 以外）
- `QuestInstance`（childId → userId へリネーム）
- `UserCollectionItem`
- `Badge` 関連
- `Streak` 関連
- `Subscription` / `UserPurchase`

## 2. タスクフロー

### 2.1 作成

- ユーザーが自分でタスクを作成する
- 親子版の「親が子供のタスクを作る」→「自分が自分のタスクを作る」に置き換え
- タスクのフィールドは同じ（タイトル、カテゴリ、曜日設定、締切、写真要否など）

### 2.2 完了フロー

```
親子版:
  PENDING → 子が報告 → REPORTED → 親が承認 → APPROVED（XP・進化）

シングル版:
  PENDING → 自分が完了 → APPROVED（XP・進化）
  ※ REPORTED ステータスを経由しない。完了ボタン一発で APPROVED に遷移
```

- 「報告」と「承認」を1アクションに統合
- 完了ボタンを押した瞬間に XP 付与・進化チェック・ストリーク更新が走る
- 既存の `approveQuestInstance()` をそのまま呼べる（承認ロジック自体は変わらない）

### 2.3 スキップ

```
親子版:
  PENDING → 子がスキップ申請 → SKIP_REPORTED → 親がスキップ承認 → SKIPPED

シングル版:
  PENDING → 自分がスキップ → SKIPPED
  ※ 申請・承認のステップなし。即スキップ
```

### 2.4 差し戻し

- シングル版では差し戻し（REJECTED）は存在しない
- 自分で自分を差し戻す意味がないため

### 2.5 ステータス遷移（シングル版）

```
PENDING → APPROVED（自分が完了）
PENDING → SKIPPED（自分がスキップ）
```

親子版の6ステップから2ステップに簡略化。

## 3. 通知

### 3.1 削除する通知

| 親子版の通知 | シングル版 |
|-------------|-----------|
| 子 → 親: タスク報告通知 | 不要 |
| 子 → 親: スキップ申請通知 | 不要 |
| 親 → 子: リマインド通知 | 不要 |
| 親 → 子: タスク追加通知 | 不要 |

### 3.2 残す/追加する通知

| 通知 | 用途 |
|------|------|
| リマインド（ローカル通知） | タスクの締切前に自分に通知 |
| ストリーク維持リマインド | 「今日まだタスクをやっていません」を夕方に通知 |
| 進化通知 | 進化・転生・バッジ獲得時のアプリ内演出（既存のカットシーンを流用） |

## 4. 画面構成

### 4.1 親子版との画面対応

| 親子版 | シングル版 | 備考 |
|--------|-----------|------|
| 子: クエスト一覧 | タスク一覧 | メイン画面。そのまま流用 |
| 子: モンスター画面 | モンスター画面 | そのまま流用 |
| 子: 図鑑 | 図鑑 | そのまま流用 |
| 子: コレクション | コレクション | そのまま流用 |
| 子: ストリーク | ストリーク | そのまま流用 |
| 親: 承認画面 | **不要** | 承認フローがない |
| 親: タスク管理 | タスク管理（自分用） | 「子供のタスクを作る」→「自分のタスクを作る」に文言変更 |
| 親: 子供の様子 | **不要** | 見る側/見られる側の区別がない |
| 親: 設定 | 設定 | 家族管理を削除 |
| ログイン選択 | **不要** | 親/子の選択画面が不要 |
| LP | 別LP | ターゲットが異なるため別ページ |

### 4.2 ナビゲーション

親子版は「親ナビ」と「子ナビ」が別だが、シングル版は1つのナビに統合:

```
┌─────────┬──────────┬──────────┬──────────┐
│ タスク   │ モンスター│ 図鑑     │ 設定     │
└─────────┴──────────┴──────────┴──────────┘
```

- タスク: 今日のタスク一覧 + 完了ボタン + タスク追加/編集
- モンスター: 現在のモンスター + 進化状況 + ストリーク
- 図鑑: モンスター図鑑 + コレクション + バッジ
- 設定: アカウント + テーマセット + サブスク管理

## 5. 共有コードと分離

### 5.1 共有する（育成エンジン）

| モジュール | ファイル | 備考 |
|-----------|---------|------|
| 進化ロジック | `evolution.ts` | そのまま |
| モンスターデータ | `monsters.ts` | そのまま（テーマセット含む） |
| XP計算 | `xp.ts` | そのまま |
| ストリーク | `streak.ts`, `streakMilestones.ts` | そのまま |
| バッジ | `badges.ts`, `badges.data.ts` | 一部バッジの条件調整（親承認系を除外） |
| コレクション | `collectionItems.ts` | そのまま |
| 日付ユーティリティ | `date.ts` | そのまま |
| カテゴリ定義 | `categories.ts` | そのまま |

### 5.2 分離する（フロー差分）

| モジュール | 親子版 | シングル版 |
|-----------|--------|-----------|
| 承認ロジック | `approve.ts`（親が承認） | `complete.ts`（自分で完了 → approveQuestInstance 呼び出し） |
| 認証 | `auth.ts`（ロール付き） | `auth.ts`（ロールなし） |
| 通知 | `push.ts`（親↔子双方向） | `push.ts`（自分へのリマインドのみ） |
| API ルート | `/api/approve/*`, `/api/family/*` | 不要 |

### 5.3 コード共有の方法

**推奨: monorepo（Turborepo）**

```
packages/
  core/                 ← 共有育成エンジン
    evolution.ts
    monsters.ts
    xp.ts
    streak.ts
    badges.data.ts
    collectionItems.ts
    categories.ts
    date.ts
apps/
  family/               ← 親子版（既存アプリ）
    src/
      app/
      lib/approve.ts    ← 親子版固有
      lib/auth.ts       ← ロール付き
  solo/                 ← シングル版（新アプリ）
    src/
      app/
      lib/complete.ts   ← シングル版固有
      lib/auth.ts       ← ロールなし
```

ただし、既存アプリのmonorepo化は大きなリファクタリングになるため、**Phase 1 では既存リポジトリをフォークして差分だけ変更**し、安定してから共有ライブラリに切り出す方が現実的。

## 6. マネタイズ

### 6.1 親子版との共通

- テーマセット（買い切り）: 同じセットを同じ価格で販売
- サブスク: 同じ価格帯

### 6.2 シングル版のサブスク差分

| 要素 | 無料 | サブスク |
|------|------|---------|
| タスク数 | 10個 | 無制限 |
| モンスター種類 | 全種 | 全種 |
| 進化 | フルサイクル | フルサイクル |
| 月限定コレクション | 全部 | 全部 |
| 季節コレクション | ロック | 解放 |
| ~~子アカウント数~~ | — | — |
| ~~親カスタムごほうび~~ | — | — |

子アカウント・ごほうびの概念がないため、サブスクの訴求ポイントは「タスク数無制限 + 季節コレクション」の2つに集約。

### 6.3 テーマセットの購入情報共有

- 親子版とシングル版でアカウントが同じ場合、購入済みテーマセットを共有できると理想的
- ただし Phase 1 では別アプリ＝別アカウントで割り切ってもよい

## 7. LP・ストア訴求

### 7.1 ターゲットの違い

| | 親子版 | シングル版 |
|--|--------|-----------|
| メインターゲット | ADHD児の親 | ADHD当事者の中高生〜大人 |
| サブターゲット | 一般家庭の親 | タスク管理が苦手な人全般 |
| 訴求メッセージ | 「子供のがんばりを親が見守る」 | 「自分のがんばりでモンスターが育つ」 |
| ストアカテゴリ | 教育 / ライフスタイル | 仕事効率化 / ライフスタイル |

### 7.2 LP の差分

- 親子版: 親向けのメッセージ（「お子さんの習慣づけを応援」）
- シングル版: 当事者向け（「やるべきことをやったら、モンスターが育つ。それだけ。」）
- シンプルさと「自分のため」感を前面に

---

## 8. 実装フェーズ

### Phase 1: フォーク＆最小差分で動くものを作る

1. 既存リポジトリをフォーク
2. Family / Role / 親子関連のコードを削除
3. 承認フローを自動完了に置き換え
4. ナビゲーションを統合（親ナビ + 子ナビ → 1つ）
5. LP を別途作成
6. Vercel に別プロジェクトとしてデプロイ

### Phase 2: 独自機能の追加

- リマインド通知の強化（締切前、ストリーク維持）
- タスクのテンプレート集（「朝のルーティン」「仕事の定型タスク」等）
- 日報・振り返り機能（1日の完了タスクを振り返る画面）

### Phase 3: コード共有の最適化

- 育成エンジンを共有パッケージに切り出し（monorepo 化）
- テーマセットの購入情報をアカウント間で共有

## 9. バッジの調整

親子版のバッジのうち、シングル版で意味をなさないものを調整する。

### 削除/変更するバッジ

| バッジ条件（親子版） | シングル版での扱い |
|---------------------|-------------------|
| 「親に承認されたタスク X 個」系 | 「完了したタスク X 個」に文言変更 |
| 「親に報告した」系 | 「タスクを完了した」に文言変更 |
| 「スキップを親に申請した」系 | 「タスクをスキップした」に文言変更 |

ロジック自体は変わらない（APPROVED 状態のカウント）。文言のみ調整。

## 10. リスクと注意点

### 10.1 自己申告の信頼性

- 嘘をついてもペナルティはない設計
- **意図的にそうしている**: 監視・ペナルティはADHD当事者のストレスになる
- モンスター育成のモチベーションが「正直にやる」動機づけとして機能するかは要検証
- 必要に応じて「写真付き完了」オプションを用意（強制ではない）

### 10.2 コードの分岐管理

- Phase 1 のフォーク方式は短期的には楽だが、長期的にはコード分岐が発生する
- 育成エンジンのバグ修正を両方に適用する手間が生じる
- Phase 3 の monorepo 化を視野に入れつつ、まずは動くものを優先

### 10.3 アカウント統合

- 将来的に「親子版の親が、シングル版も使いたい」ケースが想定される
- 同じメールアドレスで両アプリにログインした場合の挙動を決めておく必要がある
- Phase 1 では別アカウントとして割り切る
