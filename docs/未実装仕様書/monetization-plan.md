# マネタイズ設計仕様書

作成日: 2026-08-05

## 概要

QuestBoard のマネタイズは **3つの収益軸** で構成する。

1. **無料プラン** — フル機能の育成体験。ユーザー定着が最優先
2. **サブスクリプション（月額）** — コンテンツ量の拡張
3. **買い切りセット（個別購入）** — モンスターの見た目テーマ

### 設計思想

> **無料で気持ちよく使える → サブスクするともっと便利になる**

- 既存機能の閲覧制限・回数制限・機能ロックで課金動機を作らない
- 「努力の成果」に差をつけない。「コンテンツの量」で差をつける
- 迷ったら無料側に倒す。ユーザーの定着が最優先

## 2. 無料枠の詳細設計

### 2.1 子アカウント: 1人

- `Family` に紐づく `CHILD` ロールのユーザーを1人まで許可
- 2人目以降の追加時に「サブスクで解放」のUIを表示
- 親アカウント自体は制限なし

### 2.2 タスク数: 10個/子

- 親が作成するタスク定義（`Task` テーブル）が対象
- アクティブなタスク（`deletedAt IS NULL AND pausedAt IS NULL`）をカウント
- 一時停止中のタスクはカウントに含めない（再開時に上限チェック）
- 10個の根拠: 「朝の支度・宿題・片付け・歯磨き・明日の準備・習い事の練習・読書・お手伝い・ペットの世話・運動」で一通り網羅

### 2.3 進化: Stage3 + 転生（フルサイクル）

- 無料でも `Stage0(卵) → Stage1 → Stage2 → Stage3 → 転生 → 新しい卵` のフルサイクルが回る
- 進化ロジック・転生ロジックに制限を設けない
- 卵ボーナス選択（NORMAL/STUDY/STAMINA/LIFE）も無料で全種選択可能

### 2.4 月限定コレクション: 全60種

- 月限定アイテム（`m01-01` 〜 `m12-05`）は全ユーザーが取得可能
- 毎月の「新しいの来た！」感が継続利用の動機
- 宝箱ハズレ時の救済としてドロップ

### 2.5 季節コレクション: ロック

- 通常コレクション80種（春/夏/秋/冬 × 20種）はサブスクユーザーのみ取得可能
- 無料ユーザーの図鑑では **シルエット表示 + ロックマーク** で存在を見せる
- 宝箱ハズレ時の救済ドロップ対象から除外（無料ユーザーは月限定のみドロップ）
- サブスク解約後: 取得済みアイテムは図鑑に残る（剥奪しない）

### 2.6 親カスタムごほうび: 5個/子

- `TreasureItem` テーブルの `isActive = true` なレコード数でカウント
- 無効化したごほうびはカウントに含めない
- 6個目の追加時に「サブスクで解放」のUIを表示
- 5個の根拠: 「お菓子・ゲーム時間・夜更かし券・お小遣い・好きなおかず」で基本をカバー

### 2.7 標準装備（制限なし）

以下の機能は無料・サブスク共に制限なし:

- **週次レポートメール**: 親の継続利用とアプリ復帰の導線（※フッターにさりげないサブスク訴求を含む）
- **ひろば**: ソーシャル機能による定着促進
- **実績バッジ**: 全バッジが条件達成で解放される（サブスク限定コンテンツに依存するバッジは、そのコンテンツ解放後に自然に条件達成可能になる）
- **タスク履歴**: 全期間閲覧可能（ヒートマップ・月別集計含む）
- **ストリーク**: マイルストーンボーナス含め制限なし
- **チェックインカレンダー**: 締切設定・ストリーク含め制限なし
- **プッシュ通知**: 親への報告通知・親からのリマインド含め制限なし
- **XP計算**: 基本XP・締切ボーナス・写真ボーナス・宣言ボーナス全て制限なし

## 3. 買い切りモンスターテーマセット

### 3.1 概要

進化のロジック（STUDY/STAMINA/LIFE の3パス × 3ステージ）はそのままに、モンスターの **見た目（名前・画像・説明文）をセットごと丸ごと差し替える**。

| 項目 | 内容 |
|------|------|
| 価格帯 | 各 300円程度（App Store / Google Play の最低価格帯） |
| 購入単位 | テーマセット単位（1セット = 39体: Stage1×3 + Stage2×9 + Stage3×27） |
| 適用範囲 | 子アカウントごとに1つのセットを選択 |
| 切り替え | 転生時に次のセットを選択可能（進化途中の変更は不可） |

### 3.2 デフォルトセット（無料）

| セット名 | 説明 | 画像パス |
|---------|------|---------|
| **dark（かっこいい系）** | ウィズダム・ゴッドストーン等。力強い・メカニカルなデザイン | `/monsters/dark/` |
| **light（かわいい系）** | プラチナキャット・コットンラム等。動物・ファンシーなデザイン | `/monsters/light/` |

登録時またはモンスター初期設定時に dark/light を選択（既存の `side` フィールドに相当）。

### 3.3 追加セット（買い切り・例）

以下はテーマの方向性案。実際のセット名・内容は制作時に確定する。

| セット名 | コンセプト | Stage3 の例 |
|---------|-----------|------------|
| むしセット | 昆虫の成長をモチーフ | ヘラクレスオオカブト、オオムラサキ、オニヤンマ |
| とりセット | 鳥類の進化をモチーフ | フェニックス、皇帝ペンギン、ハクトウワシ |
| ドラゴンセット | ファンタジー竜 | 氷竜、炎竜、雷竜 |
| うみセット | 海洋生物 | リヴァイアサン、クラーケン、竜宮城の主 |
| ロボセット | メカ・ロボット | 巨大メカ、AI ドローン、宇宙船 |
| きょうりゅうセット | 恐竜 | ティラノサウルス、トリケラトプス、プテラノドン |

### 3.4 データ構造

```ts
// src/lib/monsters.ts に追加
export type MonsterSetId = "dark" | "light" | "insect" | "bird" | "dragon" | ...;

export interface MonsterSet {
  id: MonsterSetId;
  name: string;           // "むしセット"
  description: string;    // "昆虫の成長をモチーフにした..."
  price: number;          // 300 (円)
  isFree: boolean;        // dark/light は true
  thumbnail: string;      // セット選択UIのサムネイル画像
  table: typeof MONSTER_TABLE;  // 39体のテーブル
  eggImage: string;       // 卵の画像パス
}
```

```prisma
// schema.prisma に追加
model User {
  // 既存フィールド...
  monsterSetId    String    @default("dark")  // 現在選択中のセット
}

model UserPurchase {
  id              String    @id @default(cuid())
  userId          String
  user            User      @relation(fields: [userId], references: [id])
  productId       String    // "monster_set_insect" 等
  platform        String    // "web" | "ios" | "android"
  transactionId   String?   // ストアのトランザクションID

  @@unique([userId, productId])

```

### 3.5 適用ルール

- セットの切り替えは **転生時の卵選択画面** で行う（進化途中は変更不可）
- 切り替え後、新しい卵から新セットの見た目で育成開始
- 過去に育てたモンスターの図鑑記録は保持される（セット切り替えで消えない）

### 3.6 図鑑（セット別表示）

現状の図鑑は `side`（dark/light）に応じて1つのテーブルを表示する構成（`ZukanContent.tsx`）。
セット導入後は **複数セットの図鑑をタブ切り替えで閲覧** できるようにする。

**表示構成:**

```
📖 モンスター図鑑
┌─────────┬─────────┬─────────┬─────────┐
│ ダーク  │ ライト  │ むし 🔒 │ とり 🔒 │  ← 全セットのタブ
└─────────┴─────────┴─────────┴─────────┘

[購入済みセットのタブ]
  ├── 育てたことがあるモンスター → 実画像 + 名前 + Level
  └── まだ育てていないモンスター → シルエット

[未購入セットのタブ]  ← 39体シルエットではなく紹介カード1枚
  ┌──────────────────────────────┐
  │  🐛 むしセット               │
  │  [代表3体のサムネイル画像]    │
  │  「昆虫の成長をモチーフに…」  │
  │  [このセットを購入（320円）]  │
  └──────────────────────────────┘
```

**図鑑データの記録:**

```prisma
// 既存の collectedPaths にセット情報を付加
// 例: collectedPaths = ["dark:STUDY_STUDY_STUDY", "light:STAMINA_LIFE", "insect:LIFE_LIFE_LIFE"]
// または セット別に分離管理:

model UserMonsterRecord {
  id              String   @id @default(cuid())
  childId         String
  child           User     @relation(fields: [childId], references: [id])
  monsterSetId    String   // "dark" | "light" | "insect" | ...
  evolutionPath   String   // "STUDY_STUDY_STUDY" 等
  level           Int      @default(1)  // 同パス複数回クリア時のカウント
  firstCollectedAt DateTime @default(now())

  @@unique([childId, monsterSetId, evolutionPath])
}
```

**表示ルール:**

| 条件 | 表示 |
|------|------|
| 購入済みセット + 育てたパス | 実画像 + 名前 + Level |
| 購入済みセット + 未到達パス | シルエット（「?」表示） |
| 未購入セット | タブは🔒付きで表示。タップすると紹介カード（代表3体サムネ + 説明 + 購入ボタン）を1枚表示。39体シルエットは並べない |
| デフォルトセット（dark/light） | 常に閲覧可能（全員が所持） |

図鑑のタブには **購入済み（デフォルト含む）セットのみ** を並べる。未購入セットのモンスター39体をシルエットで埋めると情報過多になるため、未購入セットの訴求は図鑑ではなくセット購入画面（ショップ）で行う。

**カウント表示:**

```
📖 モンスター図鑑
ダーク: 15 / 39 体  |  ライト: 8 / 39 体  |  合計: 23 / 78 体
                                           （所持セット合計）
```

- 未購入セットのモンスターは合計カウントに含めない
- セットを購入した時点で分母が増える（コレクション欲を刺激）

### 3.7 サブスクとの関係

```
サブスク = 機能拡張（子追加・タスク追加・季節コレクション・ごほうび追加）
買い切り = 見た目の着せ替え（進化ロジックは同じ、完全に別軸）
```

- 買い切りセットは **サブスク非加入でも購入・使用可能**
- サブスクと買い切りは独立した課金であり、食い合わない
- 買い切りセットを購入した無料ユーザーも Stage3 + 転生のフルサイクルを体験できる

## 4. 課金インフラ

### 4.1 プラットフォーム別の課金手段

| プラットフォーム | サブスク | 買い切り | 手数料 |
|----------------|---------|---------|--------|
| **Web版** | Stripe Subscription | Stripe Payment | 3〜4% |
| **iOS (App Store)** | StoreKit 2 (IAP) | StoreKit 2 (IAP) | 15〜30% |
| **Android (Google Play)** | Google Play Billing | Google Play Billing | 15〜30% |

### 4.2 サブスクリプション管理

```prisma
model Subscription {
  id              String             @id @default(cuid())
  userId          String             @unique
  user            User               @relation(fields: [userId], references: [id])
  plan            SubscriptionPlan   @default(FREE)
  platform        String?            // "web" | "ios" | "android"（課金元プラットフォーム）
  externalId      String?            // Stripe subscription ID / Store transaction ID
  currentPeriodEnd DateTime?         // サブスク期間終了日
  canceledAt      DateTime?          // 解約申請日（期間終了まではアクティブ）
  createdAt       DateTime           @default(now())
  updatedAt       DateTime           @updatedAt
}

enum SubscriptionPlan {
  FREE
  PREMIUM
}
```

### 4.3 プランチェックの実装方針

```ts
// src/lib/subscription.ts
export async function getUserPlan(userId: string): Promise<SubscriptionPlan> {
  const sub = await prisma.subscription.findUnique({ where: { userId } });
  if (!sub || sub.plan === "FREE") return "FREE";
  if (sub.currentPeriodEnd && sub.currentPeriodEnd < new Date()) return "FREE";
  return "PREMIUM";
}

export async function checkLimit(
  userId: string,
  resource: "child" | "task" | "treasure_item",
): Promise<{ allowed: boolean; current: number; limit: number | null }> {
  const plan = await getUserPlan(userId);
  // FREE の場合のみ上限チェック
  // PREMIUM は limit: null（無制限）
}
```

### 4.4 制限チェックの実施箇所

| 制限 | チェック箇所 | タイミング |
|------|-------------|-----------|
| 子アカウント追加 | `POST /api/family/add-child` | 子追加リクエスト時 |
| タスク作成 | `POST /api/tasks` | タスク作成リクエスト時 |
| タスク再開 | `PATCH /api/tasks/[id]` (pausedAt → null) | 一時停止解除時 |
| ごほうび追加 | `POST /api/treasures/items` | ごほうび作成リクエスト時 |
| 季節コレクション | `collectionDraw.ts` | 宝箱ハズレ時のドロップ対象フィルタ |

### 4.5 クロスプラットフォームの課金状態共有

- Web で Stripe サブスク登録 → `Subscription` テーブルに記録
- iOS / Android でストアサブスク登録 → Webhook で `Subscription` テーブルに記録
- アプリ起動時に `getUserPlan()` で DB を参照 → プラットフォーム問わず同じプラン状態

**ユーザー体験の例:**

```
① Web で会員登録 + Stripe でサブスク購入（手数料 3.6%）
② App Store からアプリをダウンロード
③ 同じアカウントでログイン
④ 自動的にプレミアム機能が使える（再購入不要）
```

### 4.6 二重課金の防止

同じユーザーが複数プラットフォームで重複してサブスクを購入しないよう制御する。

**判定ロジック:**

```ts
// src/lib/subscription.ts
export async function canPurchaseSubscription(
  userId: string,
  requestPlatform: "web" | "ios" | "android",
): Promise<{ allowed: boolean; activePlatform?: string }> {
  const sub = await prisma.subscription.findUnique({ where: { userId } });
  if (!sub || sub.plan === "FREE") return { allowed: true };
  if (sub.currentPeriodEnd && sub.currentPeriodEnd < new Date()) return { allowed: true };
  // 既に別プラットフォームで PREMIUM → 購入不可
  return { allowed: false, activePlatform: sub.platform ?? undefined };
}
```

**UI での表示:**

| 状態 | 表示 |
|------|------|
| 未加入 | 「プレミアムに登録」ボタン |
| **別プラットフォームで加入済み** | **「プレミアム適用中（○○で管理中）」**（購入ボタン非表示） |
| 同プラットフォームで加入済み | 「プランを管理」（解約・変更導線） |

**管理画面での案内文:**

- Web で加入中 → iOS アプリでは「プレミアム適用中。プランの変更は Web サイトから行えます」
- iOS で加入中 → Web では「プレミアム適用中。プランの変更は iPhone の設定 > サブスクリプションから行えます」
- Android で加入中 → Web では「プレミアム適用中。プランの変更は Google Play の定期購入から行えます」

### 4.7 価格統一ルール

全プラットフォームで **同一価格** とする。

| 方針 | 理由 |
|------|------|
| 価格はストアの Tier に合わせる | App Store / Google Play は自由価格設定不可（Tier 制） |
| Web 版も同じ価格にする | プラットフォーム間の不公平感を防ぐ |
| 「Web のほうが安い」等の誘導をしない | Apple の審査ガイドライン違反になる |
| 手数料差（Stripe 3.6% vs ストア 15%）は吸収 | ストア経由ユーザーの集客コストと割り切る |

**App Store 価格 Tier（参考）:**

| Tier | 価格 |
|------|------|
| Tier 1 | 160円 |
| Tier 2 | 320円 |
| Tier 3 | 480円 |
| Tier 4 | 650円 |
| Tier 5 | 800円 |
| Tier 6 | 980円 |

### 4.8 サブスク解約時の挙動

| 要素 | 解約後の挙動 |
|------|-------------|
| 子アカウント | 既存の子は削除されない。新規追加が制限に戻る |
| タスク | 既存タスクは維持。11個目以降は一時停止扱い（自動 pause） |
| 季節コレクション | 取得済みアイテムは図鑑に残る。新規ドロップが停止 |
| ごほうび | 既存ごほうびは維持。6個目以降は自動で非活性化 |

## 5. UI/UX 設計方針

### 5.1 課金訴求の原則

- **押し売りしない**: 制限に到達した時だけ自然に表示
- **子供に直接課金UIを見せない**: 課金導線は親画面のみ
- **「今のプランでも十分使える」感を維持**: ロック表示は最小限

### 5.2 無料ユーザーへの訴求ポイント

| 場面 | 表示内容 |
|------|---------|
| 子追加ボタンタップ時 | 「兄弟を追加するにはプレミアムプランが必要です」 |
| タスク11個目の作成時 | 「無料プランではタスク10個まで。プレミアムで無制限に」 |
| 図鑑の季節コレクション欄 | シルエット + 小さなロックアイコン |
| ごほうび6個目の追加時 | 「プレミアムプランでごほうびを追加しよう」 |
| 週次レポートメールのフッター | 「プレミアムプランで季節コレクションも解放！」（さりげなく） |
| 設定画面 | 「プランを確認・変更」メニュー |

### 5.3 買い切りセットの導線

| 場面 | 表示内容 |
|------|---------|
| 転生時の卵選択画面 | 「テーマを変えて育てよう！」+ セット一覧 |
| 図鑑のセット切り替えタブ | 未所持セットはサムネイル + ロック + 価格表示 |
| 設定画面 | 「モンスターセットを購入」メニュー |

## 6. 価格設定（案）

| プラン | 価格（税込） | 備考 |
|--------|------------|------|
| 無料プラン | 0円 | — |

- **申請上の位置づけ**: 「親向けの育児支援ツール」（子供が直接課金しない設計）

### 8.2 必要な準備物

| 項目 | 内容 |
|------|------|
| プライバシーポリシー | 収集データ・利用目的・第三者提供の有無を明記。日本語 + 英語 |
| 利用規約 | サブスク条件・解約方法・返金ポリシーを明記 |

### 8.3 課金に関する審査ガイドライン

- Apple: アプリ内から外部決済（Stripe 等）への誘導は制限あり。iOS 版はStoreKit を使用
- Google: 外部決済への誘導は2022年以降一部緩和されたが、IAP 併用が安全
- 両ストア共通: サブスクの自動更新・解約方法を明示すること

### 8.4 Apple「Minimum Functionality」対策

Apple のガイドライン 4.2 は「単なる Web サイトのラッパーアプリ」をリジェクト対象としている。
本アプリは Capacitor で Web コンテンツを表示する構成のため、**ネイティブ機能を複数追加** して「アプリである理由」を示す必要がある。

**必須で追加するネイティブ機能:**

| 機能 | Capacitor プラグイン | 用途 |
|------|---------------------|------|
| プッシュ通知（APNs） | `@capacitor/push-notifications` | タスク報告通知・リマインダー（Web Push より安定） |
| 触覚フィードバック | `@capacitor/haptics` | 進化・宝箱開封・実績解放時の演出 |
| ローカル通知 | `@capacitor/local-notifications` | タスク締切のリマインダー |
| バックグラウンド検知 | `@capacitor/app` | アプリ復帰時のデータ同期 |

**将来的に追加を検討するネイティブ機能:**

| 機能 | 用途 |
|------|------|
| iOS ウィジェット | 今日のクエスト進捗をホーム画面に表示 |
| App Intents / Siri | 「今日のクエスト教えて」で起動 |
| Face ID / Touch ID | 親画面のロック（子供の誤操作防止） |
| App Clips | ファミリーコード共有時にインストール不要で子供を参加させる |

**審査通過の判断基準:**
- Web と同じコンテンツを表示すること自体は問題ない（Capacitor / Ionic 製アプリは多数通過実績あり）
- ネイティブ機能を活用し「Safari で開くのと体験が異なる」ことを示せれば通る
- 審査メモ（App Review Notes）に「ネイティブ通知・Haptics 等を活用している」旨を記載する

### 8.5 Web版とアプリ版の併存方針

Web 版は閉じず、アプリ版と併存させる。

| プラットフォーム | 役割 |
|----------------|------|
| **Web版** | LP・登録・Stripe 課金（利益率が高い）。PWA としてホーム画面追加も可能。SEO 集客の受け皿。バグ修正を即時反映可能（ストア審査不要） |
| **iOS アプリ** | App Store での集客チャネル。ネイティブ通知・Haptics 等の体験向上。StoreKit 課金 |
| **Android アプリ** | Google Play での集客チャネル。TWA ラップ。Google Play Billing 課金 |

コードベースは Next.js 1つで、アプリ版はそのラッパー（TWA / Capacitor）。保守コストの増加は最小限。

### 8.6 API 共有とバージョニング

Web 版・アプリ版は **同じ Next.js API を共有** する。API を分ける必要はない。

**構成:**

```
Web版ユーザー ──→ Next.js API (/api/*)  ←── アプリ版ユーザー
                       ↓
                   Prisma / Supabase DB
```

DB マイグレーションの影響は Web・アプリ両方に等しくかかる（片方だけ壊れることはない）。

**注意すべきポイント: アプリのバージョン遅延**

Web 版はデプロイ即反映だが、アプリ版はストア審査 + ユーザーのアップデート待ちが発生する。
そのため **古いアプリが新しい API を叩く** 状況が常に起こりうる。

**対策 1: API の後方互換を保つ**

| ルール | 内容 |
|--------|------|
| フィールド削除しない | 廃止するフィールドも 2バージョン分は残す |
| エンドポイント変更時は追加 | 既存を壊さず `/api/v2/xxx` を新設 |
| レスポンス形状の変更は加算のみ | 新フィールドの追加は OK、既存の型変更・リネームは NG |

```ts
// 悪い例: フィールドをリネーム（古いアプリが壊れる）
// v1: { quests: [...] }
// v2: { tasks: [...] }  ← quests がなくなり古いアプリがクラッシュ

// 良い例: 新フィールドを追加（後方互換）
// v2: { quests: [...], tasks: [...] }  ← 古いアプリは quests を読む、新しいアプリは tasks を読む
```

**対策 2: 最低バージョンチェック（強制アップデート）**

破壊的変更が避けられない場合に備え、アプリ起動時に最低バージョンを確認する。

```ts
// API 側: 全レスポンスヘッダーまたは専用エンドポイントで返す
// GET /api/app-config
{
  "minAppVersion": "1.2.0",    // これ未満は強制アップデート
  "latestVersion": "1.5.0",    // 最新バージョン（任意アップデート案内用）
  "maintenanceMode": false     // メンテナンス時に true にして全クライアントに告知
}

// アプリ側（Capacitor）
import { App } from '@capacitor/app';

const { version } = await App.getInfo();
const config = await fetch('/api/app-config').then(r => r.json());

if (compareVersions(version, config.minAppVersion) < 0) {
  // 「最新版にアップデートしてください」画面を表示
  // ストアのアップデートページへ誘導
}
```

**対策 3: DB マイグレーション時のダウンタイム防止**

| 方針 | 内容 |
|------|------|
| expand-contract 方式 | カラム追加 → コード更新 → 旧カラム削除の3ステップでマイグレーション |
| メンテナンスモード | 大規模マイグレーション時は `maintenanceMode: true` で全クライアントに告知 |
| ゼロダウンタイムデプロイ | Vercel のローリングデプロイを活用（デフォルトで対応済み） |
